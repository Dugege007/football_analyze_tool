# 仓库修复方案：竞彩日与顺序改按编号和精确开赛时间（草案，2026-10-08 18:25）

## 范围
- match.date 现在取自 OCR 的日期列（凌晨场可能记成自然日），也没有用星期加编号校验。
- 不少地方用「0–10 点加 24」排顺序；次日 11:00–12:00 开赛的竞彩场，main 和 私有仓 PR 都处理错了。
- LEGACY V4–V7 疑似泄漏：cutoff 小时也被套了 jc_day_hour_order。私有仓 PR 修了，但还没合；V3 不受影响。

## 做法
1. 竞彩日由编号（星期加序号）推出来，用 match.date 交叉校验，对不上就报警，不静默纠正。
2. 场次顺序和 cutoff 一律用「竞彩日加精确开赛时间」，删掉所有「0–10 点加 24」的写法。
3. 通用防泄漏断言（采纳算法顾问的建议）：每个决策用到的每一行历史数据，都必须满足「开赛时间 + 3 小时 ≤ cutoff」，跟 N5 的规则一致。cutoff 用编号得出的竞彩日加精确开赛时间来算，不用 match.date。断言写进单测，固定样例包括次日 11:00–12:00 开赛的竞彩场、凌晨 0–10 点场和跨日边界场。以后谁再写一个「加 24」，测试就会直接报错。
4. 跟 私有仓 PR 协调：在 私有仓 PR 的基础上补齐上面三条，走正规 PR 流程，不直接推 main。

## V4–V7 历史数字的处理（采纳算法顾问的建议）
- 台账（后端的 strategy_defs 或台账表）给 LEGACY V4、V5、V6、V7 标 `leak_suspect=cutoff_plus24`。修好前不再引用这些数字，也不拿来和 V3 比。前端看到这个字段就灰掉。
- 修好后用同一批场次重跑，把修前、修后的命中率和 ROI 并排放出来，差距本身就是证据。重跑结果用新版本码挂上（例如 V4-F 到 V7-F），旧行冻结保留，只作历史对照。
- V3 不打标，它的指纹不变。
