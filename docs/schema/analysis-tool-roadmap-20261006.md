# 比赛分析工具 · 整体开发路线图（2026-10-06）

> 文档性质：分析工具（作者的私有分析仓 / 「比赛分析工具」）的**目标、阶段计划、成功标准**。  
> 不替代仓库口径；仓库默认策略与结算规则未经用户同意不得改动。  
> 关联：`v1_sqlite.sql`、`v1_1_prediction_legs.sql`、`openapi-v1.1.yaml`、`backend-build-eval-20261005.md（未公开）`、`../research/methods-and-staking-survey-20261005.md`、`../backfill/schema/daily-match-scope-and-json-v2.md`、`data-conventions-v1.md`、`api/README.md`。

---

## 1. 最终目标

1. **日常运营**：分析工具替代 Excel，作为日用赛程、盘口、预测、注额与回测的统一入口。
2. **临盘派单**：每场临盘（约开赛前 1 小时；凌晨场按仓库时间窗规则）由**足球分析师**按固定格式**通知维护者**向用户发送预测消息。
3. **玩法范围（优先级）**：先做 **亚盘 / 大小球 / 欧盘 / 竞彩让球**；**比分**靠后。
4. **全量入库**：各方案、各版本的预测（含注额建议）必须写入数据库，便于回测对比与复盘；发消息不替代入库。
5. **日用消息现状**：在 OU / 1X2 / 竞彩让球数据与验证未就绪前，消息侧**仅发亚盘方向 + 简化份数**；其他玩法可先入库、不进消息。

## 3. 分阶段计划

### P0 · 工具与文档（当前）

**目标**：把契约与开发文档写齐，便于边补数边验证；不阻塞后续 API/UI。

**具体步骤**

1. **Schema / OpenAPI 文档补齐（草案可先 TODO 落表）**
   - `prediction_legs`：全策略、全玩法腿入库（已有 v1.1 草案；旧 `predictions` 亚盘不动）。
   - **资金 / 注额配置表**（`bankroll_config` 等）：固定统计本金、用户可调本金、周一资金基数、份制规则标识 —— **表字段细节 TODO，见 §5 与 `data-conventions-v1.md`**。
   - **注额计算器 API**：输入本金 / 规则 → 输出各场「份」与金额；前端可调本金 —— **路径与请求体 TODO，待后端写入 OpenAPI**。
   - **队名 / 联赛别名映射表**：中文主名 + 多对一别名（见 `data-conventions-v1.md`）。
   - **开赛时间精确到分钟**：`kickoff_at` + 遗留整点标记（见数据约定）。
   - **日期字段约定**：竞彩日 / 自然日 / 文件名 YYMM 对齐仓库（见数据约定）。
2. **注额理论与验证路径**（已有调研，不重写公式）：
   - 出处与建议：`$ODDS_DATA_DIR/research/methods-and-staking-survey-20261005.md` **第 6 章**（Kelly / 分数凯利 / Baker & McHale / 回撤闸门等）。
   - 验证路径：**影子 → 纸面 → 小注**；若搭配合适方案仍**不能稳定正期望 / 可控回撤**，整套注额规则**存档**，再调策略，不硬扛。
3. **日用消息**：仅亚盘方向 + 简化份数（§5 简化规则）；每次发送前/后保证对应策略行已入库。
4. **交叉链接**：本路线图 ↔ 后端评估 ↔ OpenAPI ↔ 数据约定 ↔ 调研备忘；协作中以本文为阶段 checklist。

**P0 成功标准** → §7。

### P1 · 数据质量

**目标**：历史手工数据可自动化消费；精确度优先于手工录入便利。

**具体步骤**

1. 排查并修复旧手工数据中的**字符 / 标点 / 队名**问题（清单见 `data-conventions-v1.md`）。
2. 开赛时间：由**整点**升级为**分钟级**；遗留仅整点记录的场次标记 `kickoff_minute_known = false`（或等价字段）。
3. 日期字段：自动化优先；建议 ISO-8601 带 `+08:00`（Asia/Shanghai）；`jingcai_date` / 文件 `YYMM.json` 与 作者的私有分析仓 对齐（细节见数据约定）。
4. 队名 / 赛事：固定**中文规范名** + 别名多对一；**消息只发规范名**；不清的先查资料再挂映射。

**P1 成功标准** → §7。

---

### P2 · 验证

**目标**：在多机构较全的场次上慢验证；不改 V3 默认。

**具体步骤**

1. 优先选用**多家机构盘口较全**的场次做验证；边补数边验。
2. 付费 API 开通后扩大覆盖面（推荐与配额见 `../research/paid-subscription-recommendation.md` 等）；当前先把工具与文档做齐。
3. 设计新方法时可**合理借鉴**仓库多层 / 多机构 / 状态机等思路；**评估旧方案可改进点**，但新方法必须新版本，且不擅自改 V3 默认。
4. 验证框架原则（防泄漏、走前、同桶对比等）见调研备忘 **第 7 章**；注额见第 6 章。
5. 注额与策略组合：影子 → 纸面 → 小注；无稳定优势则存档并调整。

**P2 成功标准** → §7。

## 5. 注额产品规则（用户已拍板）

| 规则 | 说明 |
|---|---|
| 后端统计本金 | 用**固定初始本金**做方案收益 / 回撤等统计（具体默认值 **TODO：配置项**） |
| 预测侧 / 前端 | **注额计算器**：用户可按自身情况设置本金，计算各场「份」对应金额 |
| 赛后重算 | 用户告知当前博彩账户余额后，分析师用**同一套机制**重分配注额 |
| 份制定义（草案） | **1 份 = 周一资金基数的 0.5%** |
| 单场 / 单日上限 | 单场 **0～3 份**；单日 **≤ 10 份** |
| 凯利分数 | **¼ 凯利**（细节与置信下界见调研 §6） |
| 简化档（OOS 不足时） | `|s|=… → … 份`，`|s|=… → … 份`；OOS 足够后再按 ROI 复核 |
| 失败处理 | 验证路径走完仍无稳定优势 → **存档注额规则**，调整策略后再验 |

## 10. 方案工场与消息格式（2026-10-06 增补）

### 10.1 里程碑式交付（M1–M4）

| 阶段 | 内容 | 备注 |
|---|---|---|
| **M1（当前）** | WebUI 主导航布局齐（赛程 / 预测 / 注额 / 设置 / **方案工场占位**）；v1.2 注额+别名+`kickoff_at`；队名近重复合并；V3 自检脚本；旧数据清理清单 | 功能分期，布局先整全；亚盘现页不拆坏 |
| **M2** | 亚盘稳定预测+注额+别名后：`strategy_defs` / 验证缓存表草案；配置驱动、版本化 | 不改 V3 默认 |
| **M3** | 方案编排器 MVP（配置生成；状态机用模板） | 生成可执行定义，进影子验证 |
| **M4** | 方案对比折线图 + **方案叠加**（多方案并行、统一或各自注额策略、同图资金曲线）+ 批量影子跑 | 日用白名单仍克制 |

其后：完整状态机可视化、自动脚本生成加固、OU/1X2/竞彩让球进消息（对齐原 P3）、仓库 PR（原 P4）。

### 10.2 方案叠加（portfolio stack）

挑选若干已验证方案，可：

- 同一注额策略并行；或
- 各方案各自策略并行；

在**一张**资金曲线图上直观对比统筹效果，便于多方案下注规划。排在 **M4**，与对比图同批扩展。

### 10.3 可扩展性约定

- **配置驱动**：玩法 / 机构 / 特征 / 状态机参数进 JSON/YAML 定义，避免硬编码玩法分支。
- **方案版本化**：新方法 = 新 `strategy` / `version`；旧方案可对照。
- **验证缓存按指纹复用**：同方案 + 同验证形式 + 同数据指纹命中则不重算。
- **UI 插件式占位**：导航先留「方案 / 验证 / 对比」，后接真页。
- 用户后续想法默认进合适里程碑，不堵死扩展点。

### 10.4 预测通知消息格式（已拍板）

不写「亚盘 / 大小球」等玩法名；用符号区分；份数用两个空格 + `xN`：

```
- 001 03:00 英超 曼城-阿森纳：
  主+0.5  x2；
- 002 03:30 西甲 皇马-巴萨：
  客-1.25  x1；
  大2.25  x3；
```

队名只用中文规范名。亚盘方案与功能稳定后再日常通知；此前可发示例核对格式。

### 10.5 资金规则（已拍板，供对照）

- 统计默认本金：**10000 CNY**（可改配置）。
- 单注最低 **50**；单注最高 ≤ **当前剩余资金的 50%**。
- 1 份 = 基数 × 0.5%；单场 ≤ 3 份；单日 ≤ 10 份。
- 预留人民币↔美元实时汇率（`fx_display_currency` / `fx_rates` 占位；换算逻辑后接）。
